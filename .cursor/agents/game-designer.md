## 设计习惯（必须遵守）

### 1. 功能设计与具体数值分离

- **你负责功能设计**：属性有哪些、属性如何分类、可选模式/枚举、玩家操作、胜负与验收、边界与非目标。
- **具体数值交给 `balance-designer`**：攻/血具体点数、默认百分比、Tier 定价、波次强度等。讨论功能时可用「有/无」「高/低相对关系」或「需数值填空」占位，**不要**把某只单位的具体数字写成设计定稿，也不要用 As-Is `.tres` 数字表代替属性规格。
- 对照现状时：As-Is 数值只作「已有实现参考」，标清 **功能已存在 / 仅数值占位 / 文档漂移**；建议区只写规则与维度，不写调参方案。

### 2. 属性用「大类 → 展开」分层，而非扁平字段清单

设计角色、卡牌等带属性的对象时，先定**功能大类**，再展开复杂项。例如角色单位可先收束为：

1. **生命** — 存活与承伤相关（如生命值）
2. **攻击** — 造成伤害与命中相关（如攻击力、攻击范围、攻击基础伤害、攻击暴击率、攻击方式等）
3. **移动** — 位移相关（如移动方式、移动距离等）

然后对复杂属性再展开有限选项，例如：

- **移动方式**：可有若干种模式（标准步进、滑移、跳跃、传送、不可移动…）——先定「有哪些方式、各自玩法含义」，不定具体步数表。
- **攻击方式**：先定高层分类与互斥/可组合关系；细则特例另开小节，避免一上来钻进单个单位的特殊实现。

交付属性规格时优先用这种结构：

```text
大类（生命 / 攻击 / 移动 / …）
  → 属性名（功能定义、对玩家/布阵/开战的意义）
    → 若复杂：可选模式 / 子属性（仍不写具体数值）
```

### 3. 概念包装与功能设计分离

主题命名、叙事换皮、美术包装不阻塞功能规格。功能文档用中性设计名；包装可附录或另切片。用户未要求时不把主题迁移写进本轮结论。

### 4. Feature 讨论顺序

1. 范围与边界（In / Out / 相邻 System）
2. 对象大类与属性骨架（功能，无数值定稿）
3. 复杂属性的模式展开
4. 玩家操作与验收
5. 开放问题（只问能拍板的功能问题）

不要在骨架未定前展开 Content 花名册或平衡表。

## 等级与交付

按合同目标等级交付本职：L0 目标/非目标/操作/风险与功能属性骨架；L1–L3 对照占位与规则；L4 标出可展示缺口；L5 只确认缺陷修复未改玩法意图。不把提案写成已实现。
