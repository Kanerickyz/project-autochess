# 大巴扎式 UI 壳与棋盘平铺重构方案

> 状态：**已实现并验收（L3 + GUI 证据）2026-11-06** · 分支 `feat/bazaar-ui-shell-5x4` · v6.0.24  
> 注：场景节点仍可继续拆成 StageChrome/HeroPanel 命名；行为契约（半场常驻、2+2、UiKit）已落地。  
> 参考：用户提供的大巴扎手机竖屏布局图  
> 主路径：`scenes/combat/realtime/realtime_battle.tscn` + `RealtimeBattleController` / `RealtimeArenaView`

---

## 0. 一句话目标

把战斗壳从「顶栏文字 HUD + 可变半场 Arena + 底栏 Dock」重构为**大巴扎式竖屏平铺壳**：敌我信息对称、友方阵容跨阶段常驻底半场、棋盘改为**敌 2 行 + 我 2 行（共 4 行）**，并用统一的 **Panel / Popup / Overlay** 控件语言接管全游戏交互一致性。

---

## 1. As-Is 诊断（为何有必要重构）

### 1.1 现状结构

| 层 | 现状 | 问题 |
|----|------|------|
| 顶栏 `Layout/Hud` | 遭遇名、金币、圣物条、阶段/人口/计时文字 | 信息散、不像「玩家面板」；与半场脱节 |
| 中部 `ArenaView` | 5×8 格 + 双方 **4×5** 座位铺满半场 | 竖屏信息过密；与参考图「两行卡带」不符 |
| 底栏 `Dock` | 手牌 / 开战 / 招募 HUD 动态塞入 | 阶段切换时高度锁定、样式内联 `StyleBoxFlat.new()` |
| 阶段模式 | 招募/地图商店：队伍画到**上半场**；候选人/货架占下半场；胜后半场 slide 出场 | **友方半场不常驻**，与需求 4 冲突 |
| 主题 | `project_theme.tres` 仅 Button/Panel 基础色 | 无 Panel 变体、无 Popup/Modal 约定；各屏自行造样式 |
| 体量 | `realtime_arena_view.gd` ~4.6k 行、`controller` ~4.3k 行 | 壳层与绘制/阶段逻辑耦合，难统一 UX |

### 1.2 与文档冲突（必须先拍板）

| 来源 | 已定稿 / As-Is | 本次用户诉求 |
|------|----------------|--------------|
| `AGENTS.md` / `DeckConfig` | 棋盘 **5×8**，座位 **4×5** 铺满半场 | 敌我各 **2 行**，合计 **4 行** |
| 招募 / 地图商店 / 附魔 | 阶段内重布半场（队上货下或炉上队下） | **友方半场跨阶段一直可见**（参考大巴扎） |
| Notion `feature-combatlevel` 等 | 权威在 Notion（本地仅指针） | 需同步改规格，否则实现与文档分裂 |

**结论：有必要重构壳层与布局契约；不宜只做皮肤微调。** 但棋盘几何与阶段信息架构属于玩法边界，应先定规格再动代码。

## 2. 目标体验（玩家语言）

1. **一眼看清**：敌方面板 / 敌阵两行 / 中线 / 我阵两行 / 我方面板 / 主操作按钮，纵向一屏平铺。  
2. **常驻我的队伍**：准备、战斗观战、招募、地图商店、附魔等阶段，**底部友方两行座位始终在**；阶段内容改占「敌区 / 顶区货架 / 底栏操作区」，而不是把我方阵容挪走或滑出。  
3. **操作少跳页**：金币、圣物/神器、英雄态、主 CTA 与阵容同屏；细节用 Popup，不做整页替换（全屏结算/事件等例外见 §4）。  
4. **控件同行为**：所有 Panel 同材质层级；Popup 同遮罩、关闭、主/次按钮位置；触控热区与反馈一致（对齐 `apple-hig` 技能约束）。

## 3. 推荐信息架构（大巴扎手机壳）

竖屏自上而下固定带（命名建议）：

```text
┌─────────────────────────────┐
│  StageChrome（天数/层数/设置） │  ← 薄顶栏
├─────────────────────────────┤
│  EnemyHeroPanel             │  ← 敌头像、血条、小圣物/状态圆标
├─────────────────────────────┤
│  EnemyBoard（2 行座位）       │  ← 战斗=敌阵；非战斗=预览/空/阶段货架溢出
├─────────── Midline ─────────┤
│  AllyBoard（2 行座位）★常驻   │  ← 全阶段可见；可换座（规则允许时）
├─────────────────────────────┤
│  PlayerHeroPanel            │  ← 血/资源、头像、圣物条、金币宝石
├─────────────────────────────┤
│  ActionDock（阶段主操作）     │  ← 开战/继续/刷新/撤销等 CTA
└─────────────────────────────┘
         Popup / Modal 盖在壳上（不明抢半场）
```

★ = 跨阶段不卸载、不 slide 出屏；最多做高亮/锁定/半透明禁用，不搬家。

### 3.1 各阶段上半场用途（保证友方常驻）

| 阶段 | 上半场（原敌区） | 下半场 AllyBoard | ActionDock |
|------|------------------|------------------|------------|
| 准备 | 敌人预览座位 | 己方站位（可拖） | 开战 / 刷新 |
| 战斗 | 敌单位作战 | 友单位作战（观战） | 加速等 |
| 招募 | **候选人货架**（原下半场内容上移） | 己方队伍常驻 | 锁定/完成招募 |
| 地图商店 | **消耗品+装备货架** | 己方队伍常驻（可换座） | 离开商店 |
| 附魔 | **熔炉槽** | 己方队伍常驻 | 确认/离开 |
| 店\|事选择 / 事件 / 圣物三选一 | 可用居中 **Popup/Modal**；壳底层仍显示 AllyBoard（或压暗） | 常驻 | CTA 在 Modal 内 |

这与当前「招募把队伍画到上半场」相反，是本次最大行为变更。

## 4. Widget 设计契约（需求 1）

建立统一 UI Kit（建议路径，实现阶段再建）：

| 类型 | 角色 | 规则 |
|------|------|------|
| **ShellPanel** | 嵌在主壳内的常驻块（HeroPanel、BoardFrame、Dock） | 无模态；不挡全屏；共享边框/材质 token |
| **FloatingPanel** | 非模态浮层（单位信息卡、圣物详情条） | 可点外部收起；不锁输入到半场以外必要区域 |
| **Popup** | 轻确认 / 二选一（店\|事、卖出确认） | 半透明遮罩；主按钮右/下、次按钮左/上；Esc/遮罩可关（毁灭性操作除外） |
| **ModalScreen** | 重流程（事件全文、败北结算、设置） | 全屏或近全屏；打开时壳可保留底阵剪影；必须有明确退出 |
| **Toast** | 短暂提示（层级解锁等） | 不抢操作；自动消失 |

### 4.1 UX 交互原则（全项目同一套）

1. **主操作唯一**：每屏/每阶段只强调一个 Primary CTA（颜色/尺寸对齐主题 Primary）。  
2. **同控件同反馈**：按下缩放、禁用灰态、可拖高亮用同一 Tween 曲线表（可落在 `UiMotion` 小模块）。  
3. **详情不跳页**：长按/点按单位 → FloatingPanel（沿用现有长按信息卡思路）。  
4. **色不唯一通道**：敌我除红/绿血条外，位置（上/下）与图标形状区分。  
5. **禁止新屏私建 StyleBox**：一律走 Theme type variation 或 UiKit 工厂。

### 4.2 Theme Token（建议）

扩展 `resources/ui/project_theme.tres`（或拆 `ui_shell_theme.tres`）：

- `PanelContainer` 变体：`ShellPanel` / `HeroPanel` / `PopupPanel` / `DockPanel`
- `Button` 变体：`Primary` / `Secondary` / `Icon`
- 颜色：敌血、我血、金币、描边、遮罩 alpha  
视觉风格继续服从纸片中世纪幻想（`PAPER_CUTOUT_ART_BRIEF`），参考图只借**布局密度与层级**，不照搬大巴扎木纹材质除非美术另开任务。

## 5. 棋盘几何（需求 3）— 推荐草案

### 5.1 推荐（与「一共四行」字面一致）

| 项 | 新值 | 说明 |
|----|------|------|
| 逻辑棋盘 | **5×4** | 中线 `mid=2`；敌行 y=0..1，我行 y=2..3 |
| 座位 | **2×5** / 侧 | `DeckConfig.DEFAULT_SEAT_ROWS=2`，`COLS=5`；铺满半场 |
| 上场人数上限 | 保持 `deploy_cap` 独立 | 满座 ≠ 上场上限（现有语义保留） |
| 备战行 | 仍可贴在 AllyBoard 下沿或 Dock 上沿 | 不占用 4 行战斗格 |

影响面：`BoardHalf`、`PrepareSlotBoard`、遭遇 `board_size`、生成/测距、几乎所有 `Vector2i(5,8)` 测试、半场 slide 像素计算、招募候选人行几何。

### 5.2 备选（若希望保留更深走位）

- 逻辑仍 **5×8**，但**座位只占近中线的 2 行**（每侧 2×5），后两行作机动空间。  
- 优点：战斗走位深度保留；缺点：竖屏仍偏空/偏高，与参考图「四行卡带填满」不一致。  

**方案默认推荐 5.1**；若战斗手感不能接受变浅，再退回 5.2。

### 5.3 明确不在本次做的

- 不把单位改成大巴扎「固定物品格、不对撞走位」规则。  
- 仍是座位入场 + 开战后自动战（现有 realtime 行动队列）。  
- 不重做单位美术；只调格尺寸与壳布局。

## 6. 友方半场跨阶段常驻（需求 4）

### 6.1 壳状态机（概念）

引入 `BattleShell`（或重构 Controller 的表现边界）：

- `ally_board`：**单一数据源**（`PrepareSlotBoard` / `DeckState` 座位），全阶段绑定同一视图节点。  
- `enemy_or_stage_board`：按阶段切换数据源（敌座位 / 候选人 / 货架 / 熔炉），**不再**把队伍 `configure_grid(..., enemy_side=true)` 画到上半场。  
- 删除或废弃胜后「友方 slide 出屏再从屏外滑入」作为招募入场主表现；改为上半场内容替换 + 轻过渡。

### 6.2 代码落点（高风险文件）

- `realtime_battle_controller.gd`：`enter_recruit` / `enter_map_shop` / `enter_enchant`、`_rebuild_recruit_team_slots`、`_hide_combat_chrome_*`  
- `realtime_arena_view.gd`：`recruit_active` 上队下候选绘制分支、`ally_half_slide_y`  
- `map_shop_battle_extension.gd` / `enchant_battle_extension.gd`  
- 相关 `*_test_runner.gd`（大量断言「队伍在上半场 / 4×5 / 5×8」）

### 6.3 玩家信息平铺（需求 2）

- 将金币、圣物徽章条从顶栏文字行下沉到 **PlayerHeroPanel**（参考图右下资源盒 + 头像两侧圆标）。  
- 敌方镜像 **EnemyHeroPanel**（准备/战斗显示敌预览；招募阶段可改为商店招牌/层数信息）。  
- 顶栏只留层数/天数 + 设置。

## 7. 实施分期（建议）

> 原则：先定规格与壳契约，再改几何，再迁阶段，最后收敛旧屏。避免一次巨型 PR。

### 里程碑 A — 规格与契约（设计，少代码）

1. 用户拍板：§5.1 vs §5.2；阶段表 §3.1；Popup vs 全屏边界。  
2. 更新 Notion：`feature-combatlevel`、`feature-player`、`feature-game-loop` / 招募与地图商店相关页、必要时 `arch-overview`。  
3. 落一份实现侧短文（可放 `Documents/DesignNotes/` 指针或 Notion Note）：Widget 表 + 壳带示意图。  
4. （可选）只读拉 `ui-designer` + `game-designer` 审布局与走位深度。

### 里程碑 B — UI Kit + BattleShell 骨架

1. Theme type variations + `UiKit`/`ShellPanel`/`GamePopup` 场景。  
2. 重构 `realtime_battle.tscn` 节点树为 §3 带状壳（可先仍 5×8/4×5，只改壳）。  
3. Player/Enemy HeroPanel 接上金币与圣物条。  
4. 验收：准备/战斗视觉壳可用；旧阶段逻辑暂兼容。

### 里程碑 C — 棋盘改为 2+2

1. `DeckConfig` / 默认 `board_size` → 5×4 + 2×5；迁移遭遇与测试。  
2. 修正 `BoardHalf`、座位生成、备战行 y。  
3. 跑座位/战斗/运动相关 runner；调单元格视觉缩放。

### 里程碑 D — 跨阶段友方常驻

1. 招募：候选人改上半场；AllyBoard 不搬。  
2. 地图商店 / 附魔同构。  
3. 去掉友方半场出场 slide；保留可选敌区/货架过渡。  
4. 更新 flow / recruit / map_shop / enchant 测试断言。

### 里程碑 E — 收束一致性

1. `ShopOrEventChoicePanel` / 主题 / 圣物等玩家选择题改走 Arena 上半场 `StageChoice` 卡片（非全屏窗）；设置等非对局选择仍可用 Popup/Modal。  
2. 清理各处内联 `StyleBoxFlat.new()` 重复。  
3. GUI 验收对照参考图：四行、底阵常驻、主 CTA、信息平铺。  
4. bump `application/config/version`（玩家可见）。

## 8. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 5×4 战斗深度变浅、技能距离失效 | 先做沙盒对局手感；不行则切 §5.2；距离类技能回归测 |
| Controller/Arena 过大难改 | 壳节点先拆场景，逻辑用 facade，避免同 PR 重写 9k 行 |
| 测试大面积红 | C/D 分 PR；先改常量与 helper，再改断言 |
| 与 Notion 不一致 | A 完成前不合并玩法几何到 main |
| 参考图材质期望 | 布局优先；材质跟纸片风，单列美术任务 |
